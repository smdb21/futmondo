# Player/round score matrix

The canonical observations remain in `player_match_observations`. Every row identifies a player, championship, season, scoring version, round, source score status, and observation time. Corrections are retained as revisions rather than overwriting the historical record.

`player_round_points_latest` projects the latest revision for each complete identity key. A latest NULL score stays unknown; the view does not resurrect an older numeric value. It uses the existing `player_round_context_revision` index. A second index or a physically wide table is unnecessary. The view is `security_invoker=true`, has no PUBLIC/anon/authenticated grants, and grants SELECT only to the server service role. Credentials remain on the R server. This follows the [Supabase view/RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security#views).

`read_league_round_points(championship_id, max_rows=50000L)` loads the league's latest observations as one logical batch. REST pagination uses deterministic player/season/scoring/round order, 1,000-row requested pages, and actual returned row counts. Short server pages are followed until an empty page; the maximum-row cap produces explicit partial coverage. N is not a query parameter. Callers must preserve the season and scoring scopes when calculating averages. The result is a long-form matrix that can be indexed or pivoted locally without additional database queries.

## Shared database-first acquisition — 2026-10-30

The current table path is `read_league_round_dataset(championship_id, max_rows=50000L)`. It reads `player_round_dataset` once per retained root-session league/team dataset, with deterministic REST pagination. The view combines latest score revisions with latest successful acquisition checks, including players whose returned history was explicitly empty. `read_league_round_points()` remains available for compatibility and the focused score-reader checks. N never enters either query.

`new_shared_round_points_controller()` is owned by the root Shiny session. The Today, My Team, All Players, and other table module namespaces register their active context and visible IDs with this controller; they do not create separate league loaders. Each table selects its players from a shared published matrix and calculates its requested N locally. An inactive page does not initiate player reads. At most two retained league/team entries share a 50,000-row stored/live score budget; old inactive entries are evicted when asynchronous reads or live observations reach that budget. Catalog acquisition is capped at 2,000 IDs; only normalized observations are retained. Logout and account replacement clear private state before reading dependent league/team reactives.

Saved successful checks are fresh for 24 hours when season and scoring are known, or one hour when either context is unknown. A fresh legacy score observation receives the same reuse window without being relabeled as a successful endpoint check. Reuse requires exact championship/season/scoring context; gaps, unknown scores, and a missing appearance alone do not require another API call. A conflicting/incomplete saved window can be repaired from a confirmed, round-anchored fitness snapshot as described below. Known and unknown seasons remain separate. No startup live probe is required. An explicitly unknown source context cannot authorize use of a different known context.

Initial acquisition visits only absent/stale catalog histories, with visible players first and two API requests in flight. A successful response is attempted once per active-session dataset, including an empty response; errors remain explicit until Refresh or a new session. Manual Refresh forces only the current table's player IDs, including when primary loading temporarily hides optional content. It does not invalidate every catalog player's history. Acquisition pauses at the existing write-queue backpressure thresholds and resumes from write-completion signals. Navigation makes outstanding callbacks obsolete, retains completed work, and starts no new player requests until an active table returns.

Migration `20261030234619_player_round_dataset.sql` adds immutable `player_round_history_checks` rows keyed by championship/player/season/scoring/checked_at and the server-only `security_invoker` union view. Latest-by-timestamp selection prevents a late older check from replacing a newer check. These are factual league observations shared across authorized server-side league reads; private runtime resources remain account-specific. No historical scores or check markers were manufactured from existing observations. See [production application and rollback evidence](round_dataset_migration_20261030.md).

`get_player_summary()` retains `points_received`; `recent_points_summary_valid()` rejects a missing field, malformed container/round/score, stale response, or error rather than treating it as an empty history. Explicit empty points and NULL scores have distinct valid meanings. `persist_recent_points_snapshot()` submits an ordered bounded job: score chunks first, then a success-check marker. `defer_persistence(..., on_complete=...)` acknowledges only after every operation succeeds; an earlier failed write prevents the marker, and queued/active cancellation settles all coalesced listeners as unsuccessful. Cancellation may remain in the existing account-level persistence diagnostics; the table's saving message tracks this dataset's own outcomes. A marker proves a successful source check, not that every player appeared in every round.

Shared matrix assembly/publication is bounded to five-second intervals, with an immediate initial snapshot or newly settled visible group. Off-table completions update progress without repeatedly assembling or rebuilding the visible table. Switching pages can immediately publish already acquired scores for the new visible IDs. Module wrappers update their local history only when their player subset or the league-round anchor changes.

## Saving source last-five snapshots — 2026-10-30

The user confirmed that `average.fitness` represents consecutive league rounds, oldest to newest: `2,5,12,12,6` has 6 in its latest represented round. `recent_points_fitness_rows()` carries only each player's vector, original source `observed_at`, and available context from the active tables and already-loaded catalog (at most 2,000 players). It does not manufacture a timestamp when that source time is absent. Catalog and table rows from different observation timestamps do not share an anchor.

A complete agreeing saved window avoids both writes and a source probe. Database maximum rounds are used only for this work-avoidance comparison; they never authorize new round assignments. When a snapshot needs repair, the existing two-slot queue requests one qualifying player's explicit round history, even if legacy rows are fresh. `recent_points_fitness_anchor()` requires exact player/league/team/account/season/scoring context, a probe observation time at least as new as the snapshot, and at least two distinct known scores. Exactly one consecutive window in the returned source history must match every known position, and that window must end at the latest explicitly reported source round. A repeated pattern, old-only match, conflicting context, empty/failed probe, or sole constant vector cannot establish an anchor. Neither upcoming rounds, current-round subtraction, nor the database maximum supplies an anchor. No authentic HAR or live account response was verified for this change.

`recent_points_fitness_observations()` then maps the same snapshot's vectors to explicit rounds. The vector length must equal `min(5, latest_round)`; a shorter vector is accepted only for that early-season prefix. Zero, negative points, and unavailable slots keep their positions; unknown slots are never compressed or replaced by zero. For a verified round-10 anchor the example maps to rounds 6–10, last-four mean 8.75 and last-three mean 10. Unknown finality stays unknown.

`recent_points_fitness_changes()` skips unchanged values and equal/newer existing revisions, including NULL corrections, so a new snapshot does not downgrade known finality. Changed observations join the shared matrix and enter observation-only `supabase_post_direct` jobs of at most 100 rows with the existing full identity conflict key. Fitness writes never create `player_round_history_checks`; only an actual successful summary endpoint check follows the existing score-first, marker-last acknowledgement path. Failed fitness batches remain available for explicit Refresh; they are not automatically retried. Pending and failed buffers deduplicate full player/context/round keys and are each capped at 10,000 rows. The existing owner/global queue budgets and 50,000 retained-score budget remain in force.

Mapped fitness supplies requests up to five rounds without a per-player source replay. The `required_rounds` registration field preserves older-history acquisition for visible N>5 demand; a five-score snapshot is never treated as a full-history fetch. Switching N within the available five-round window is local. Anchor attempts and successes retain at most 32 snapshot entries per root dataset, canceled probes can resume on navigation, and the existing publication throttle avoids per-player table rebuilding. The dynamic `Avg Last N` column appears immediately after Name. All shared player tables default to descending average order with unavailable values last; users can change the sort. The column retains numeric data and renders only a rounded number or an empty missing-value cell, with no coverage or reported labels. Installed reactable infers its numeric type from that data (`colDef` has no `type` argument); `sortNALast=TRUE` controls missing-value order.
