# Finance worker progress and resolved context

The initial worker integration made finance output depend on the entire historical scan and every prepared child resource completing. It discarded the accounting controller's existing intermediate publications. Production also retained an unresolved current-finance job alongside the resolved job for the same account/league/team; both lanes acquired/replayed the same source history. The user saw an indefinite-looking spinner despite many acknowledged source responses. An old run later failed with generic `resource_parse`; that old diagnostic does not establish its exact exception.

## Context ownership and durable evidence

`worker_finance_context_matches(descriptor, membership)` checks only the current `fm_worker_finances` pipeline against source-verified account membership: competition and season must be known and match; known scoring must match; the reference team must be explicit. Other factual/historical resource handlers keep their existing contracts. Admission, claim and lease continuation use this pure JSON predicate. `fm_worker_finance_source()` waits for resolved competition/season before requesting a finance job.

Apply `scripts/migrations/20261112035000_resolved_finance_jobs.sql` and then `scripts/migrations/20261112035500_finance_progress_publication.sql` before deploying the matching R/Python changes. It pauses ineligible current-finance jobs (`due_at=infinity`, `context_unresolved`, no lease) without deleting or rewriting their observations, snapshots or checkpoints. Unknown archives are never aliased to the current known season/scoring scope. Existing blocked-sport and account/league/generation/leader guards remain. The new predicate is SECURITY INVOKER and executable only by the server role.

Production migration is recorded as `20261112035051_resolved_finance_jobs` (source SHA-256 `9ad41b439fcf6368db5d73e4b2c10b8a784c5c713922363013211966d16fff25`). Verification found the unresolved duplicate inactive with all 131 response checkpoints retained; the resolved job continued. This is recovery of existing opted-in factual acquisition, without transactions, new consent, authentication changes or data deletion.

## Incremental finance publication

The direct accounting controller `shared_rival_finance_source(..., refresh=NULL, on_update=NULL)` accepts an optional callback receiving the same factual calculation value it publishes internally. Ordinary UI callers leave it NULL. Only the private headless R helper installs the persistence callback; encoding and database waits stay outside Shiny's serving process.

`fm_worker_headless_finances(env, auth, context, on_update=NULL)` forwards the callback. The actual helper sender emits a progress request only when the existing accounting result contains at least one finite estimated balance and no calculation error. It copies the controller value, preserves its ledger/confidence/missing-data/source times, and marks it loading while the remaining scan or resource saves continue. Unknown values remain unknown; no alternate accounting formula or zero-filling is introduced.

The private JSON pipe adds:

```json
{"type":"progress","result":{"value":"<existing typed codec node>","observed_at":"<source UTC>","checked_at":"<UTC>","status":"partial","completeness":"partial","ready":false}}
```

The actual `value` is a typed object, not a string. Python restricts this message to finance jobs, forces partial status/completeness, and uses the existing `worker_publish_child` RPC with the exact parent descriptor/key. Chunks and manifest must be acknowledged before returning `{ok:true,published:true}`. This updates the visible durable finance resource without settling the parent job or releasing its lease. Its context and source age remain intact, and existing UI polling reads only the changed version. Failed writes remain retryable; they do not count as a successful preview. Cached valid snapshots continue to be reused across sessions/restarts.

Both sides cap ordinary publications to once per 15 seconds and suppress unchanged helper output. One prepared (`ready=true`) preview may bypass that interval so users need not wait for all child resources to persist. It still remains partial and loading: `ready` is a controller milestone, not proof of full historical coverage or job completion. Only final parent publication settles the job. The per-lane cadence/ready markers reset for the next job. Stale previews do not automatically requeue an already-running resource; explicit manual Refresh still records a subsequent run.

## Saved award reuse and finality

The helper reuses scoped persisted Best XI/MVP selections only when all 11 identities are valid, finality is explicit, persistence is acknowledged, available season/scoring fields match the current context, checks are less than one day old, and no later settlement requires rechecking. Missing, malformed, foreign, provisional, unknown-finality, expired or settlement-flagged selections still acquire and persist source evidence. A source-confirmed finished round is passed to the existing official-selection parser as finished, rather than dropping that catalog evidence at the helper boundary. This retains the existing finality/settlement accounting contracts and daily correction audits.

`scripts/migrations/20261112035500_finance_progress_publication.sql` adds a nullable publication `run_id` to snapshot metadata and preserves the existing guarded publisher signatures. A current finance aggregate can replace its own loading preview when discovering older input moves its conservative source time backward; source dates are not renewed to force ordering. Independent child observations still retain the newer-source guard across different runs. This avoids a final result being discarded while its job incorrectly appears finished. Production recorded `20261112041332_finance_progress_publication`, source SHA-256 `0555cd85f1b84622188a6d7758f6c8d0c0620ac63fdb014a690f23f7ab0e954e`.

The existing ten-minute controller wait now reports the fixed safe `finance_timeout` code when that actual condition occurs. Arbitrary exception messages remain private. This diagnostic is not used as a substitute for acquisition or correctness checks.

## Safe timeout queue diagnostics — 2026-11-12

Dokploy logs confirmed another actual `finance_timeout` at `2026-11-12T08:00:12Z`; package masking messages are ordinary R startup output. The plain timeout code did not identify the remaining queue. The private helper now attaches a bounded counter code at the existing ten-minute controller timeout: `s` is seed completion (0/1), `b` active reads, `q` queued reads, `o` pending ownership reads, `t` directory row count, `ts` the enumerated directory status, followed by queued counts for saved/seed/team/lineup/ranking/notifications/ownership/ownership_catalog tasks. Counts are integers from 0 to 9999. Unknown task names, source IDs, tokens, response bodies, accounting values and arbitrary exception messages are never included.

Python accepts only the exact ASCII counter grammar or the legacy plain timeout code; other failure text remains `resource_parse`. The sanitized code follows the existing warning and leased job-failure persistence path, so Dokploy logs and server-only job metadata can reveal what remains pending without exporting private snapshots or adding database tables. This is diagnostic instrumentation, not certification that finance preparation or historical reconciliation is fixed. A production timeout after deployment is needed to identify the pending state; existing observations, source timestamps, durable partial calculations and retry behavior are unchanged.

Performance: diagnostics run once on an existing timeout, take one pass over the already bounded queue, and add no requests, database writes, polling, timers, UI redraws or retained response data. Private helper/Python assets are excluded from the R deployment bundle, with no dependency or manifest change. The dedicated regression exercises the actual timeout branch using a synthetic clock and checks counter bounds and private-field exclusion; Python checks the exact grammar and rejects appended/private/malformed codes. The normal accounting and offline application lifecycle checks remain required.

## Historical lineup backlog recovery — 2026-11-12

The production diagnostic `s1_b2_q43_o0_t10_tsready_...team1_lineup42...` established a loaded seed/directory with a team repair behind the historical lineup backlog. A later server metadata check showed the same pattern with one team repair and 74 queued lineups. Current-season saved team histories were present, but no current-season `round_lineup` records had been persisted. These checks returned counts/status only, without exporting private snapshots.

Three changes address reproduced acquisition/persistence costs:

- `persist_rival_finance_evidence()` measures the actual serialized JSON byte length against its existing 256 KiB row budget. It previously measured expanded R objects: a synthetic full-detail lineup occupied over 752 KiB in R but only 80,867 JSON bytes, and was silently filtered out before persistence. It is now queued with the full raw lineup, formation/details, source timestamp, ownership IDs and revision signature intact. Scope filters, the JSON limit, database limits and acknowledged write/retry behavior remain in force. Truly oversized/foreign rows remain rejected.
- Team point-history repairs are prepended to the queue. Ordinary lineup scheduling waits until pending team reads/repairs finish. `lineup_pending` tracks queued and active lineups across success, rejection and generation resets. The controller retains its existing labeled calculation through that batch and rebuilds from accumulated evidence at drain; it does not advance cached calculation inputs while retaining the prior value. Existing pending flags, incomplete evidence notes, revised-signature protection and the accounting engine still determine the result.
- The private helper does not wrap its seven controller-only acquisition envelopes as additional typed shared snapshots: seed, team observation, lineup observation, ranking observation, notification page, player ownership observation and ownership calendar. Their underlying HTTP checkpoints and normalized database evidence remain durable; ordinary display getters still use shared snapshot publication. This avoids extra resource lookups and redundant typed copies of detailed raw lineups. No factual history is removed, and no memory cache replaces database persistence.

Existing warning logs now include a validated function-handler name as well as the fixed error code and lane. This allows later `resource_parse` failures to be attributed without logging exception messages, IDs or private response bodies. The supplied historic parse lines did not contain a handler, so their exact causes are not inferred. `access_revoked` is a lease/admission failure code and is not, on its own, proof of a rejected Futmondo password/token; current account metadata reported enabled/active. No authorization guard was weakened.

Validation: the regression runs the actual controller for ten teams/twelve finished rounds, saves all 120 matching lineups, verifies repairs precede lineups, and records three accounting builds. A fresh controller then reuses the saved lineups with zero new lineup acquisitions and identical final balances. A baseline replay of the prior controller reproduced a repair after lineups and recorded five builds in the fast-response fixture; production-duration responses can trigger more throttled intermediate builds. The existing known-answer 100-minus-10 ledger, lineup revision race, historical reconstruction, persistent calculation cache, ownership batches and classification rendering remain covered. A separate real private-helper run with 120 synthetic roughly 80 KiB detailed lineup HTTP replies completed with loading false and all 120 evidence writes acknowledged in 168.69 seconds locally. This is a synthetic bridge benchmark, not hosted HTTP/database throughput or a production completion claim.

Performance review: repairs run earlier without additional source requests; lineups with unchanged signatures reuse persisted evidence on later sessions/retries. Batch bookkeeping uses scalar counters and the existing bounded queue; it adds no timers, polling, worker lanes or serving-process background work. Measuring JSON size adds serialization before writes, limited to the current acknowledged batch of 50; it permits larger expanded R objects for source records that fit the wire budget, so rich histories still have material memory/serialization costs. Avoiding duplicate typed task snapshots offsets some of that cost. The original ten-minute timeout, source age, unknown/partial states and acquisition checks remain unchanged. No VM sizing/capacity claim is made.

The R manifest was regenerated and inspected, with only this runtime checksum staged alongside the task. `.rscignore` now explicitly excludes `.codex-attachments` after verification found local user screenshots entering a regenerated manifest; the Docker allowlist already excluded them. Tests, internal docs, helper source, captures, credentials and backups remain outside the R bundle. No dependency, environment or database migration is needed. Automatic deployment and production completion/current-season lineup persistence are separate acceptance checks.

Batch validation was explicitly checked with 51 records: the first 50 are submitted, and the final detailed record is only validated/submitted after the first write is acknowledged. The 5,001-record synthetic admission call fell from 1.969 seconds with up-front serialization to 0.442 seconds with bounded validation; remaining serialization occurs through existing acknowledgment-driven continuations. This is local admission timing, not hosted DB latency.

## Verified historical archive reuse — 2026-11-12

Acceptance of `854e630` confirmed the repair left the backlog (`team0`), but the run still timed out with 48 lineups and one notification page queued. Current-season lineup persistence remained zero. A read-only identity join then found 99 saved unresolved-context lineup records: every record's opaque round/team identity appeared in the current authoritative team-round histories for the same account and league. All 99 also had revision signatures, explicit boolean eligibility, closed status labels and populated player arrays. This establishes candidates, not permission to alias an unknown archive into a current season.

`get_rival_finance_saved()` now optionally returns a separate `archive_lineups` candidate list and `archive_lookup_status` (`ok`, `partial`, `unavailable`). Only a known current competition/season with absent team-round lineup pairs triggers the account/league-scoped backend lookup: eligibility records in the `lineup:` namespace with at least one unknown scope dimension, at most 600 rows in pages of 50. Candidates never enter accounting evidence directly. A complete current set skips the lookup. Read failures or limits remain explicit statuses and ordinary source acquisition remains available.

`rival_resolve_archived_lineups(candidates, context, rounds, awards, existing=list())` is a pure validator. It requires the exact account/league, compatible existing context dimensions, a unique current authoritative team-round ID, confirmed closure, the exact current round/award revision signature, a valid original source observation time, populated ownership IDs, and explicit historical eligibility/closed status. Ranking supplements alone cannot prove archive scope. Unknown current identity, foreign known context, changed revisions, malformed data and conflicting same-time observations are rejected. The newest compatible archived source record takes precedence; a newer revision that fails matching cannot expose an older matching one. Existing known lineup evidence is never overwritten by archive recovery.

The controller can then create a current-context record with the same source timestamp, ownership/eligibility/raw fields and signature, plus `context_resolution` provenance recording the method and original competition/season. The original archive remains intact. This is resolution from authoritative opaque source identities and an exact current revision, not inferred dates, synthetic season identity or wholesale archive relabeling. Records pass through the same acknowledged, idempotent database persistence path before final worker success; only the affected saved-evidence memory key is invalidated. An accepted source ID skips redundant lineup acquisition. Unmatched candidates remain unavailable and follow ordinary acquisition/revision checks; no values become zero.

Focused validation covers all acceptance/rejection boundaries, conflicting/latest records and existing-known preservation, bounded DB query construction, lookup skipping, and the actual controller's scoped persistence without a new lineup request. Its independent ledger is 100 opening cash + 1 recorded payment + 5 Best XI + 10 MVP = 116. Performance: the new candidate query adds backend reads only for missing known-context lineups, with a 600-row/50-row-page bound and no source HTTP request.
