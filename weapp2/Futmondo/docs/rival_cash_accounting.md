# Rival cash accounting

Rivals now shows numeric **Reconstructed balance**, sorted descending, with separate **Confidence**, **Last updated**, and debt status. There is no opening-cash column. Expanding a row shows the recorded and estimated components, missing evidence, and the difference between reconstructed cash and an accessible authoritative balance. No balancing adjustment is invented.

## Sources and interfaces

`rival_finance_runtime.R`, sourced by `futmondo_functions.R`, implements:

- `normalize_money_movements(answer)`: decoded movement array or nested `answer` array. Preserves `_id`/`id`, concept, type, category, signed amount, date, and optional explicit bonus/round/player/source identifiers. A missing amount stays `NA`; descriptions never establish a reward category. `complete` means the returned rows parsed successfully, not that all historical activity is covered.
- `read_rival_finance_evidence(account_id, championship_id, season, max_rows=20000)`: one logical paginated read of `rival_finance_evidence_latest`, scoped by the authenticated account, league and explicit season. `get_rival_finance_saved()` also reads the league opening-cash default. Legacy transfer archives without a verified season/reset boundary are excluded. Restricted database credentials stay on the server.
- `build_rival_cash_dataset(..., account_id, season="unknown")`: pure calculation returning `team_finances`, per-team `breakdowns` and `cash_ledgers`, the existing shared `pressroom`, and compatibility `all_purchases`. Missing account context fails closed. Supplied evidence is filtered again by account/league/season. The caller must supply the same season for award/eligibility inputs; optional context columns are checked when present.
- `rival_finance_directory(teams)`: selectable league-team rows before financial sources settle. Unavailable cash, reconciliation and squad values remain numeric `NA`; observed directory points/value can still display.
- `shared_rival_finance_source(...)`: one root-session dataset, saved data first, followed by bounded asynchronous source refreshes. The directory resolves independently of award/financial readiness, with explicit loading/unavailable state. Late directory arrivals enqueue each team once per refresh; source callbacks never evaluate potentially pending UI dependencies. A league/account switch clears old data and invalidates late callbacks. Same-context navigation reuses the session result.

Opening cash comes from retrieved league configuration when present. Otherwise league `5b55f9d767214483120b87cf` uses the user-confirmed €300,000,000 per team, also stored in `league_cash_defaults`. No other league inherits that fallback. A recorded opening allocation replaces the separate opening amount; it is not added twice. Multiple budget allocations require reset/season evidence.

## Recorded money and estimates

Immutable movement revisions use source identity `(account, league, season, team, movement ID)`; the latest observed revision replaces its earlier amount. Distinct payment IDs remain distinct, including additional payments after postponed matches. The movement ledger takes precedence over the pressroom transfer ledger as a whole: feeds without common identities are not added together. Unclassified recorded reward income suppresses potentially overlapping estimates. A historical payment with explicit round/player/reward identity suppresses the corresponding estimate. Season points are never multiplied by a rate and presented as already-paid cash.

Full ideal-XI selections and their separate MVP flag are retained. Verified historical eligibility can attribute both components, using historical rules where available and explicitly labelled current-rule assumptions otherwise. Current roster ownership is never used to assign old rewards. The legacy settlement-evidence adapter remains compatible with explicitly recorded payments. Normal rival reconstruction now obtains published team-round scores and historical lineups directly; it does not require synthetic `verified`, `points_credited` or `round_settled` flags. Repeated player-level legacy evidence is deduplicated to one team/round/reward; conflicting amounts or historical owners are excluded.

The primary amount always comes from reconstruction, including when observed cash is accessible. **Reconciled** means that reconstructed amount numerically matches an authoritative budget observed within five minutes; it does not erase evidence gaps. **Reconstructed** requires complete accounting and no unresolved assumptions. **Estimated** labels the reconstructed subtotal when current rules, historical membership, missing ownership or other identified gaps remain. `observed_cash`, `observed_cash_fresh`, the fresh-only compatibility `budget`, and `reconciliation_difference` retain observed zero/negative values separately. A private official budget is optional; its absence never prevents calculation or display of the reconstructed balance. Successful movement parsing alone does not establish historical completeness. A user-confirmed opening amount does not itself reduce confidence.

## Running cash history (2026-10-31)

`rival_cash_entry()` gives every included source component an amount, source, type, optional payment date, round/player identity and estimate marker. `rival_cash_ledger()` orders opening cash first, actual dated movements chronologically, and undated components separately. Equal timestamps use stable source IDs; their exact within-timestamp order is not claimed. Known pressroom IDs keep the latest input revision; unknown IDs are preserved instead of being collapsed together. Movement revisions and bonus-overlap rules above remain authoritative.

The complete ledger is accumulated once before UI projections. Its last `running_balance` is both `reconstructed_cash` and the primary `estimated_cash`; display sorting, pagination and filtering cannot recalculate a balance from a subset. A recorded opening allocation replaces configured opening cash. Ambiguous reset allocations remain visible with `included=FALSE` and an exclusion explanation, rather than silently becoming extra cash. Missing amounts remain `NA`; their excluded contribution is identified as a known-amount estimate. A missing opening amount leaves every balance unavailable. Zero and negative cash remain numeric.

The Rivals history reuses `cash_ledgers[[team_id]]`. Every dated transaction has a **Money left after (estimate)** value, including transactions within the same minute. **Components without payment dates** presents round rewards and undated movements using a **Calculation subtotal** column. This is reconciliation arithmetic, not an invented payment timeline; these amounts are explicitly excluded from the dated historical balances until their separate reconciliation section. The final subtotal matches the reconstructed summary. No observation time, round completion time, or current time is substituted for an unknown payment date.

`rivals_cash_history_rows()` is a view-only projection, and `rivals_cash_history_widget()` renders paginated rows. The transaction tab and player pivot perform no additional movement/pressroom retrieval. Transfer summary cards reuse the same `total_spent`/`total_sales` source precedence, excluding opening cash, bonuses and fees from squad purchases/sales. Observed cash is shown separately with freshness and its difference from reconstruction; no balancing transaction is inserted.

## Publication and split rounds

The shared MVP source reads all saved XI members. New snapshots replace the complete selected-player set for the round, including removed recipients, and preserve nullable scores. The legacy selection table remains intact. Saved snapshots are read for display; acquisition requires an explicit Round MVPs/Admin action. **Refresh provisional or changed rounds** or **Refresh selected round** rechecks the catalog before fetching a replacement selection. General Refresh reloads the saved catalog, and changed notifications mark coverage for recheck; neither starts automatic historical award acquisition. The explicit controller caps acquisition at 120 round tasks with at most two reads in flight.

Notifications are refresh signals only. Neither notification text nor the existence of an official XI creates a financial movement or proves final settlement. A changed list observed in Notifications also invalidates the active-session round/finance refresh key; this does not run unattended collection. Point payments may be partial, while ranking and ideal-XI payments wait for the whole round according to [Futmondo's postponed-match rules](https://help.futmondo.com/article/228-procedimiento-en-partidos-aplazados).

Supplied HAR captures establish league reward configuration and empty preseason team-round responses. The public [Futmondo web client](https://cdn.mondocore.com/futmondo/assets/js/futmondo.v5.3.2.js) establishes the nonempty team-round and historical lineup field names plus `top`/`flop` ranking direction. No authenticated live replay was used. Historical roster-only award recipients, the precise ownership cutoff for their awards, manual adjustments hidden from public feeds, and notification-to-round identity remain genuine source gaps; missing award ownership identifies the exact round/player IDs. Empty/malformed award responses cannot erase a known selection; a validated revised nonempty selection can. Exact cash for every rival is not claimed.

## Performance and verification

The root dataset caps retained evidence at 20,000 latest identities. Reads use 1,000-row pages, team refreshes cap at 100 teams with at most two composite requests in flight, and each team movement response caps at 5,000 rows. The existing async adapter retains its 32-request budget per composite read. Evidence revisions cap at 256 KiB each; writes use sequential 50-row batches through the existing bounded queue. No writes trigger table updates. UI publications are coalesced to at most one per two seconds during background progress, with one cancelable trailing callback so the last update is delivered, plus immediate directory/source/final-state updates; detail tables paginate ten rows. Existing global cache/queue limits still apply.

Focused tests cover revisions, notification non-payments, signed/unknown money, separate XI/MVP components, historical eligibility, overlap avoidance, partial settlement, duplicate/conflicting settlement evidence, account isolation, saved navigation reuse, delayed-request heartbeat and a maximum of two in-flight reads. Independent accounting validation is recorded separately. `test/test_shiny_simulation.R` is the mandatory offline lifecycle harness. Hosted latency and real Futmondo payment contracts require separate verification.

The applied schema and live database checks are documented in [rival_cash_migration_verification.md](rival_cash_migration_verification.md).


## Direct historical reconstruction (2026-10-31)

The intended rival result is opening cash + signed transfers + point income + round-ranking income + ideal-XI/MVP income + known signed adjustments. Summary cards and the numeric, sortable league column both present this reconstructed balance; they do not wait for a rival's private balance.

`get_rival_team_finance_observation()` now reads `/1/userteam/rounds` once per team alongside the existing information/movement observation. Its source array contains `id`, `number`, `points`, `status` and optional `negative`. A successfully validated full array replaces that team's prior full array, including round removal/reset. Failed HTTP/API/format responses cannot erase saved history; only an explicitly successful empty response can clear it. Snapshots use the existing scoped evidence table with `evidence_type="eligibility"`, `payload.kind="team_rounds"`, and `source_id="rounds:TEAM"`; no migration is required. Up to 120 round records per team are accepted.

`rival_historical_components()` prepares one shared dataset of completed per-team rounds. Published points multiplied by the configured point rate produce the point subtotal. Running/next rounds and cumulative totals are not converted to cash. The source `negative` flag excludes a team from all automatic premiums. A saved matching historical lineup can supply a missing flag. If both sources omit it, eligibility is an explicit estimate assumption, not a claimed verified fact. The existing recorded-payment overlap rules apply; negative fees remain signed adjustments and do not suppress unrelated derived rewards.

Ranking allocation follows [FAQ142](https://help.futmondo.com/article/142-configura-las-primas-automaticas-en-un-campeonato-social), its [linked official calculator](https://jsfiddle.net/ukvqdr7u/14/), and [FAQ134 on tied prizes](https://help.futmondo.com/article/134-en-caso-de-empate-a-puntos-entre-dos-usuarios-cual-prevalece-en-la-clasificacion). `top` favors the highest points and `flop` the lowest. All-participant weights are N through 1 over N(N+1)/2, with JavaScript-style rounding per slot. Three places use 50/30/20 percent and five use 40/30/15/10/5 percent. Ties share their occupied slot amounts. Known negative-start teams do not participate; unknown flags and historical membership are labeled assumptions. All directory teams need a completed round score before allocating its pool; an explicitly unfinished official award selection also excludes that round's ranking reward.

Missing completed historical lineups are retrieved through `/1/userteam/roundlineup` with `{championshipId, userteamId, round: ROUND_ID}`. Saved starter and `bench.players` IDs establish positive historical ownership; `negative` supplies debt eligibility. These snapshots use `payload.kind="round_lineup"` and `source_id="lineup:TEAM:ROUND"` in the same evidence store. A player absent from the lineup/bench is not assumed absent from the historical roster. Conflicting owners or eligibility states block the affected reward. Current-rule use remains labeled because the historical reward configuration at kickoff is not returned by this endpoint.

One active-session queue loads at most two composite reads concurrently. The one-time historical lineup batch caps at 600 tasks; each saved final lineup is reused across navigation and later sessions. A signature of source round points/status/eligibility and the official selection triggers only affected round refreshes after corrections. Saved lineups with a stale signature are excluded while replacement is pending. Revised scores and XI lists replace their earlier components instead of adding a second payout; distinct recorded money movement IDs still add exactly once. Existing coalesced UI publication, bounded evidence retention and deferred persistence apply. No polling, per-player fetches, dependency or schema changes were introduced.

## 2026-11-01 — Cash-flow reconciliation and observed bonus/transfer types

The ledger is now the sole input for signed cash, inflow, outflow and running balance. **Total inflow includes starting cash exactly once**; total outflow is the magnitude of every included negative entry. Their difference equals the reconstructed final balance. Numeric purchases/sales include transfers whose method lacks evidence; their identified ordinary/clause subtotals and a separate coverage notice do not discard any amounts. Missing source amounts still remain missing, with a known-amount limitation; no artificial balancing entry or zero is created.

`rival_normalize_movements()` canonicalizes observed `buy`, `clause`, `sell`, `clause_sell`, `ranking` and `budget` types before all summaries and overlap checks, preserving source type/category. Ranking becomes a position reward, with numeric round labels mapped to the catalog and split settlement labels such as `1.1`/`6.2` preserved. This also repairs old saved evidence whose optional `bonus_type`/`round_id` fields were blank. Positive clause sales no longer suppress unrelated rewards as unidentified income.

`rival_classify_transfers()` uses a source event identity first, otherwise a unique matching player ID/exact display name, participating team and direction, exact amount and timestamp within one second. The one-second tolerance covers sub-second source-recording jitter; it does not treat a multi-day clause-completion delay as an established match. Conflicts and ambiguous candidates remain unknown. Confirmed methods propagate to both sides of the same pressroom event. Current clause price, missing bids, price equality alone and current ownership are never used. Pressroom persistence now writes nullable `is_clause` for unknown rival transfers instead of hardcoding false, preserving System transactions as ordinary. The migration protects known classifications during null replay/unique legacy adoption without adding financial rows.

MVP and Best XI player calculations are grouped into separate round reward rows with expandable player/amount details; position and point rewards remain separate. Recorded payments replace corresponding estimates, including round-level award payments without a player ID. A typed reward with no round identity suppresses potentially overlapping estimates of that type while preserving its recorded amount and allowing independently identified other reward types. A single unambiguous non-split recorded league position-payment time anchors reconstructed position/MVP/XI entries, using the user's confirmed simultaneous-payment rule and retaining the reconstructed marker. Split labels or multiple payment events require phase-specific selections: the latest full reward remains visibly undated rather than being assigned to the first/last payout or paid twice. Distinct recorded payment IDs remain separate. Unknown combined award payments are not split unless their components can be established; conservative overlap guards remain.

The missing historical lineups had a concrete loading-path defect: `/1/userteam/roundlineup` was absent from the cooperative asynchronous adapter's read allowlist. It is now explicitly allowed as a factual read (also in the synchronous retry allowlist). The existing two-read, signature-based bounded lineup queue can actually retrieve and persist eligibility. Failed/malformed lineup results report that affected award bonuses remain excluded; today's roster is never a fallback. Captured official client code supports the existing `championshipId`, `round`, `userteamId` request and `players`, `bench.players`, `status`, `negative` response contract.

## Saved bonus recovery and missing historical participants (2026-11-02)

`rival_evidence_decode()` now unpacks nested data-frame list columns row by row. PostgREST JSON simplified by `jsonlite::fromJSON()` can represent `payload` as a data frame whose `players`/`rounds` columns already contain each snapshot's complete records. Keeping a one-item wrapper around that frame previously made an eleven-player XI look like one malformed player, so `award_saved_rows()` correctly rejected it and no historical lineup demand followed. The decoder preserves nested record arrays, source scope, scoring metadata, unknowns and malformed-record rejection; it does not bypass XI/finality validation. A sanitized production-shaped batch recovers all 11 saved XIs (121 players) and 99 team-round rows. Rounds 1–10 are closed/final; running round 11 and its unknown award finality remain excluded.

If completed team-round history is missing for a directory member, the shared source can now retrieve `/1/ranking/round` with `championshipId`, numeric `roundNumber` and the current `userteamId`. This exact query and response contract come from the supplied official Flutter client (`bph` → `cyM`, metadata `ceH`, ranking rows `c5T`); it issues one request and consumes the ranking array without pagination. Only a closed response with distinct nonempty team IDs and finite points establishes the historical participant set. The current directory can include a team absent from that historical ranking. Such a team receives no invented score, membership flag or allocation row; missing point history remains explicit. Returned historical participants supply the ranking denominator, including former members; only current displayed teams receive resulting ledger entries.

A ranking snapshot is persisted in `rival_finance_evidence` using existing `evidence_type="eligibility"`, `payload.kind="round_ranking"`, and `source_id="ranking:<round_id>"`. The payload contains the requested round identity/number, observed metadata status, original ranking records, source directory IDs and a signature of the known team-round inputs. Changed inputs invalidate its use. Valid snapshots supplement only missing participant round rows. No table migration is needed. `rival_saved_rankings()` validates once and retains parsed rows; `rival_supplement_rounds()` reuses those rows. Historical preparation indexes lineup snapshots and reuses signatures within one publication.

Ranking retrieval waits for the ordinary team reads to finish, then queues at most one task per missing round/signature, up to 120 per refresh. The existing two-read concurrency limit applies to rankings and lineups together. Persisted unchanged rankings and lineups are reused after navigation and new sessions; failures cannot create zero points or synthetic bonuses. A league shaped like the observed data can have an initial backlog of about ten ranking reads plus ninety historical lineup reads, followed by saved-data reuse. No polling or unattended worker was added. Live ranking/lineup retrieval and actual save acknowledgements have not been verified in this change.
