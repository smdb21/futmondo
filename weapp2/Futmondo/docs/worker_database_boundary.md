# Database-only browsing and autonomous collection

For opted-in accounts, factual data follows one direction: Futmondo → Python/R worker → database → Shiny. The browser polls saved versions; page navigation, expiry, local cache invalidation, login renewal and Refresh do not enqueue, prioritize or reschedule acquisitions. Non-opted-in sessions retain interactive acquisition. Explicit transactions, their live preflights/readbacks, login-time coach consent, and account/preferences settings remain separate user actions.

The reported recurring queue had several concrete causes: missing/stale UI reads re-enqueued jobs every30 seconds; some query families existed only after a browser requested them; completed core jobs could become due again after5–15 seconds; recurring high-priority work starved history; the reserved short slot could remain idle with eligible short work elsewhere. Empty argument lists and inherited page context also produced different resource keys for the same account endpoint. Earlier repaint fixes did not correct these acquisition dependencies.

## Database and scheduling

`worker_account_descriptor(account, handler)` produces the exact canonical account-only descriptor used by R. The `worker_seed_enrollment` trigger inserts one discovery job when access is enabled/renewed, without changing an existing due time. Existing enabled accounts receive a missing canonical seed during migration. Disabling still removes jobs and ciphertext under the existing consent contract. `worker_read(account, versions, descriptors={})` accepts at most128 scoped descriptors and1MiB, performs only reads, and supports legacy two-argument callers. It can resolve an unknown context to a unique authoritative current context even when neither the requested alias nor a derived view has a job. Known season/scoring/account/player/argument mismatches remain rejected. Snapshot descriptors are persisted with parent/child publication and indexed by account, handler and argument hash; source observations are not relabeled. Fully known contexts exit peer lookup without querying candidates.

`worker_next_refresh_due` schedules completion plus the configured interval, even if the returned source observation is already stale. Validity is not renewed. `worker_claim` gives due query families turns based on their last dispatch, then chooses the oldest due job in that family. The short slot prefers core observations and helps other short reads when core is caught up; long finances/capacity composites stay on the general slot. A single-slot installation also retains family fairness. Quiet hours, consent, excluded/blocked leagues, generation checks, leases, account source serialization and existing rate/connection limits remain. These are schedules, not completion guarantees; a large initial backlog still takes time to acquire.

Old card-history jobs are retired because selected cards now read summaries plus stored point/price history. Existing snapshots/history are preserved. Legacy recent-point/clause jobs are retired only after a summary worker successfully publishes their durable replacement. Duplicate account-only jobs are retired only after a canonical replacement exists. Legacy capacity jobs are normalized to300 seconds while their original15-second action validity remains strict.

## Source acquisition and persistence

`fm_worker_discover()` now covers resolved context, core and rival data, authoritative historical lineup/award/round references, capacity display, and pending-transfer player summaries independently of UI visits. Discovery reads already-saved dependencies through the bridge; it adds no source HTTP. A missing bootstrap dependency is retried by the next scheduled parent cycle. Arbitrary GUI reference hints do not define finalized award identity; round IDs and finality still do. One catalog registers three source families per player rather than four, removing527 duplicate recurring jobs for a527-player catalog.

`worker/summary_views.R::fm_worker_summary_views()` derives recent points and clause observations from a successful player summary. It verifies identity and source state, writes normalized history plus completion markers/clause evidence through acknowledged worker persistence, then publishes typed derived snapshots. `worker_history_persisted=TRUE` exists only after those writes succeed; Shiny cannot invent acknowledgement. Negative points and genuine zero are retained. The GUI can project already-fetched fitness data but does not write it back as new factual history in worker mode.

Child results carry their policy interval and stricter original deadline. Python uses the minimum of declared validity and original source time plus that interval. Capacity's15-second deadline is not extended to its300-second collection schedule. Persistence failure prevents successful derived publication. Existing DB snapshots remain durable across browser/process/container restarts; memory only accelerates reads.

## Shiny and manual actions

Worker fetch/peek/poll and invalidation contain no acquisition enqueue call. Refresh coalesces a database reread. Expiry publishes one truthful stale state; unchanged polls do not repeatedly redraw it. Expired saved clauses return as observations rather than waiting120 seconds for a fresh source read. The status banner shows actual active collection and actionable failures, not recurring due jobs as an endless page-loading count. Player cards subscribe to relevant stored revisions and retain account/player isolation.

Opening an offer is explicit manual intent. If saved capacity is too old, the offer dialog performs one asynchronous live verification; all nested prerequisites bypass the worker store. A late result cannot affect another account/team/player/dialog. No source fetch occurs from merely opening a card, and uncertain mutations are never automatically retried. Final submission retains its existing independent preflight. Database-only getters without authentication arguments use their existing asynchronous DB reader rather than becoming nonexistent worker jobs.

## Verification and performance

Synthetic SQL tests run the new read function inside a read-only transaction, verify exact R/SQL enrollment-key parity, resolve a cold derived snapshot without creating jobs, enforce context/request limits, retire duplicate derived jobs only after publication, preserve fixed intervals/quiet hours and exercise fairness with527 waiting player jobs. Seven family claims measured about0.3 seconds locally; this is not VM latency. The initial version measured5.2 seconds and was corrected with the known-context lookup fast path before release.

The GUI regression runs two cold sessions and12 polls/session spanning six simulated minutes, plus Refresh and20 cache invalidations: zero source calls, acquisition enqueues or GUI history writes. A527-player history replay also completes with zero GUI writes/source reads while requiring durable-marker proof. Browser tests at360/1440px show zero idle banner/card redraws across two real polls; changed balances paint once and Refresh creates zero acquisition jobs; heartbeat65/99ms and no horizontal overflow. Worker source/discovery, codec, known-answer point transformations, child deadlines, card revision updates, explicit manual-offer isolation and the required offline lifecycle are tested separately.

Performance review: same service/slot/source-rate limits and same five-second changed-version DB poll. Acquisition pressure falls by removing GUI demands, early rescheduling and redundant source jobs. Discovery is bounded and DB-only; published values/facts remain acknowledged and bounded. The scheduler groups the bounded job table by account/handler; canonical snapshot lookups use an index and skip known contexts. New functionality adds no dependency/environment variable.
