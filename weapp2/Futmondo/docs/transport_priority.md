# Bounded interactive request scheduling

`async_transport.R` schedules requests before giving their handles to libcurl. At most four requests run at once, using the existing four-connection pool. The global admission limit is 32 logical operations across ordinary writes/authentication and factual reads, including queued requests and reads waiting to retry. A read and its current HTTP handle consume one admission together.

`async_adapter_fetch(..., priority = NULL)` selects `interactive` for the top-level `get_team_acquisition_capacity`, `get_acquisition_capacity`, `get_player_summary`, and `get_my_market_players` handlers; other handlers default to `normal`. An explicit `normal` or `interactive` override is supported. Every replay stage retains this priority. The team-capacity handler delegates to `get_team_acquisition_capacity_async()` when available, preserving its owner, current-context predicate and priority.

`fm_async_read_http(..., priority = "normal")` coalesces by its existing request-and-owner identity, independently of priority. An interactive consumer promotes the existing queued HTTP request and any later retry. `fm_async_http(..., timeout = 15, priority = "normal")` queues one physical request without adding automatic retries. Existing positional arguments remain unchanged.

Within each priority, dispatch remains FIFO. While both classes wait, one ordinary request dispatches after at most four interactive dispatches, preventing ordinary history saves and reads from starving. Active requests are never interrupted. `fm_transport_cancel(owner)` removes that owner's queued and active HTTP requests, rejects their promises, cancels factual-read backoff timers, and removes the transport pump timer when no requests remain.

The internal `fm_transport_admitted()` counts logical reservations without double-counting their physical handles. `fm_transport_schedule()`, `fm_transport_pump()` and `fm_transport_start()` manage one cooperative timer and four active slots. `fm_transport_finish()` releases each physical request once. Queued task environments retain only request arguments, owner, priority, optional logical-read key, active handle and promise continuations; they remain bounded by the admission limit. `dispatch_read_key` is set only around a synchronous admission call to associate a factual read's handle with its existing reservation, including retries.

Network and connection timeouts begin when a slot is assigned. Previously every handle entered libcurl immediately, and libcurl counted time waiting for an available connection against both timeouts; a request could time out before reaching the source. This behavior is documented by [libcurl's connection-limit reference](https://curl.se/libcurl/c/CURLMOPT_MAX_TOTAL_CONNECTIONS.html). Queuing adds no retry: the existing factual-read policy still allows at most two attempts for eligible transient errors, and authentication/manual actions remain single-attempt operations.

## Verification and performance

`Rscript test/test_async_transport_priority.R` exercises actual curl sockets against `test/http_priority_fixture.cjs`, a loopback-only synthetic server. Its nine groups cover queued timeout exclusion, priority across sequential requests, FIFO/fair dispatch, promotion during coalescing and retry backoff, the combined 32-operation admission limit, cancellation, adapter-stage propagation and explicit overrides, synchronous dispatch cleanup, and single-attempt manual writes. No accounts, credentials or transactions are used.

The contention fixture makes the same 12 requests with both policies and observes no more than four simultaneous requests. Four availability stages require 80 ms of synthetic source work. A measured run completed those stages in 751 ms at ordinary priority and 189 ms at interactive priority, with the event-loop heartbeat preserved. A separate fixture proves that a request queued behind 250 ms of work completes with a 100 ms network timeout once its own 20 ms response starts; the old libcurl queue times out before that request reaches the server.

Queue scans are bounded by 32 entries; dispatch adds no API/database requests or dependencies. Request metrics count physical dispatches, so cancelled queued work is not counted as a sent request. These are isolated measurements, not production latency guarantees: an already-running slow request still occupies its slot, and network delays or unrelated synchronous R work can still delay readiness. The scheduler does not extend source-data freshness deadlines; availability assembly must independently verify that its prerequisites are still fresh.
