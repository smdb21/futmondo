# Home and saved pages

Both password login and remembered login open Home. The dashboard tab `login` presents Welcome to visitors and Home to signed-in users. Home shows the active league selector, team, round, balance and squad size. It links directly to the main pages. Account settings contains display timezone, factual sync preferences and logout. The page controls adapt to the screen size and the Home control remains reachable with the sidebar collapsed. The server checks administrator access before offering Admin.

## Floating Home and Refresh controls

On signed-in pages other than Home, the lower-right corner holds two labeled buttons, **Home** and **Refresh**. They share a width and a 48 px height and sit inside the device's safe area. Both stay visible on desktop, including when the sidebar is collapsed.

At viewport widths of 767 px or less, scrolling the page or a scrollable area within it reveals both buttons. They stay visible for three seconds after the last scroll, then fade. Tabbing to either button reveals the pair and keeps them visible while keyboard focus is inside. Reduced-motion mode changes visibility immediately when the idle delay ends. The public welcome and Home omit the floating row.

Home opens the top of the signed-in dashboard and moves focus to its heading. Pressing Refresh immediately shows “Requesting league refresh…” above the button and keeps the page open. The result stays visible for six seconds, including when scrolling stops. A queued refresh updates balances and players as new data arrives. If the request fails, the message explains how to retry. [League refresh behavior](database_first_sync.md#explicit-league-refresh)

## League overview and saved destination

Home reads the active account and league's saved calendar, team, roster, market offers and transfer observations. The balance and squad size cards label stale figures in words. The overview omits observation timestamps. The Round schedule card shows the kickoff date and time in the account’s display timezone. The next row labels the countdown “Time until kickoff” and displays units for days, hours, minutes and seconds.

`home_round_context(rounds, now)` returns the current round, the next scheduled group and the next instant at which the display can change. `home_round_windows()` groups the saved kickoffs and splits a confirmed long gap between completed and outstanding games. `home_round_phase()` uses the match results and the official round status to distinguish **In progress**, **Awaiting remaining fixtures**, **Awaiting round closure** and **Closed**. When play and closure are both unconfirmed, Home shows **Awaiting round status**. An advanced game and the resumed fixtures retain their original round number. Home follows the intervening matchdays during the gap. The next scheduled group has its own kickoff and countdown, including before the season starts.

Balance uses the same manual-finance projection as the Balance summary. **Active offers** shows the manager’s outstanding outgoing offer count and combined euro amount, including confirmed changes while saved figures catch up. The row loads independently of the cash figure. Squad value and the unfiltered squad’s net 24-hour market-value change follow it. Squad value uses the saved team valuation or the sum of a complete roster’s known market values, as in My Team. The Squad size card shows **Players value** with green rising and red falling counts. A second row shows verified incoming and leaving players from the same pending clause-transfer records as My Team. Each direction has a text label and an arrow. The Transfers row shows a single “Loading…” while either count is pending. A count that is already available keeps its direction label. If the completed read cannot verify the count, that direction shows “Unavailable”. A complete empty direction displays zero. Below Transfers, **Scheduled clause buyouts** appears for the selected team when at least one scheduled purchase is active. Expand the count to see each player, reserved amount, opening in the account timezone and current purchase status. Both cards use the same roster summary. An unchanged price contributes to neither count. Missing player changes leave the trend unavailable while the saved balance can still display. The trend and `observed_squad_count()` share one roster read. A confirmed empty roster yields zero players and zero movement.

`page_preferences.R` persists the last visited destination under the authenticated Futmondo `userid`. An allowed saved destination becomes a **Continue to…** shortcut on Home, available across browsers, leagues and new Shiny sessions. New accounts and accounts with obsolete or unauthorized preferences still see the ordinary Home destinations. Returning to Home preserves the last destination. Following a shortcut or choosing a destination uses the same application navigation as the sidebar.

`fm_navigation_pages(is_admin)` returns the tab IDs, labels, icons and descriptions used by the sidebar and Home. `fm_saved_pages(is_admin)` uses those tab IDs as its allowlist. `fm_page_store(user_id, page = NULL, visited_at = NULL, owner)` asynchronously reads one row or upserts `user_id`, `page` and the UTC visit timestamp through the bounded HTTP transport, with an eight-second timeout per attempt. Startup reads use the reserved interactive transport slot and can retry once after a transient network error or HTTP 408, 429 or 5xx. Preference writes are single attempts. Retry and subsequent navigation can resubmit an unacknowledged preference. Only server credentials access the table. Database `recorded_at` records persistence time. An update trigger rejects older visits arriving from concurrent sessions. The account/page data has no expiry.

`fm_page_preferences(session, login_token, page, is_admin, store)` returns the `last_page` reactive used by the Continue shortcut. Reading a preference only updates the available shortcut. There is one logical read per account login and at most one in-flight write per account in the current session, coalescing further changes to the latest visit. Active saves may finish after logout or session closure using the captured account ID. Late reads cannot change the active page or leak another account's shortcut. Failed writes retain the latest pending visit for Retry or subsequent navigation while the process remains active. A read failure exposes Retry and leaves Home's other destinations available. Reading a preference, visiting Home and reselecting an acknowledged saved destination add no writes.

Apply `scripts/migrations/20261107050308_user_page_preferences.sql` to existing databases. New databases include the same objects in `scripts/schema.sql`. RLS is enabled, public/browser roles have no privileges or policies, and `service_role` has only SELECT/INSERT/UPDATE. The trigger uses SECURITY INVOKER and an empty search path. The configured hosted database received the migration and corrected account-ID constraint on 2026-11-06 (Pacific time).

## Historical startup transport recovery (2026-11-13)

The saved-page error reported with the blinking screen has no confirmed database rejection: aggregate logs contain one preference HTTP 200 at 2026-11-14 01:19:28 UTC. That status alone cannot establish successful delivery and decoding in the client process. The previous path discarded failure details and immediately left a Retry banner after any transient failure. Final transport/parser failures now log only the allowlisted `user_page_preferences` resource, safe category, optional HTTP status and reference. No account identifier, credential, response body or raw exception text is logged. Malformed successful responses remain errors, and are never interpreted as an empty preference or retried as transport failures. The precise failure in that production session cannot be recovered from the previous diagnostics.

`fm_async_read_http(..., timeout=15)` now accepts an optional positive per-attempt network timeout. Timeout participates in the transient coalescing identity; retries preserve the caller's timeout and priority. Existing calls retain the default 15 seconds. Queue admission remains bounded at 32 logical requests and four sockets; the page restore adds no polling, persistence table, or memory cache. A normal successful startup still performs one database GET. A transient failure may perform one additional GET, while navigation remains responsive during backoff. Focused checks reproduce a first-attempt 503 followed by a saved-page restoration, terminal network/401 failures, malformed 200 bodies, single-attempt writes and cancellation during backoff. Existing transport fixtures measured the reserved foreground request at 42 ms while three 400 ms background requests remained active, with the same four-socket cap. These are local synthetic timings, not a production latency guarantee.
