# My Team clause visibility and sale profit

My Team passes the application's existing `league_settings_source` into its player table. `players_table_renewal_disabled(settings)` merges league and primary-team configuration with the primary values taking precedence, matching Admin. Only an explicit `configuration.ddt = true` (including boolean strings) hides **Suggested Clause**. Missing, pending or unrecognized values remain distinct from a prohibition; a subsequent configuration update changes the table schema. **Owner team ID** is omitted from this table's display, while the original row IDs remain available to player-card and transaction handlers.

My Team opts into `get_reactable_columns_for_players(..., show_sale_profit = TRUE)`. **Selling by** and **Offer** retain sortable numeric amounts. Their cells show the prospective profit or loss on a separate line below the full euro price, for example `12.000.000 € (+2.50 M€)` or `12.000.000 € (-0.25 M€)`. The parenthetical uses millions, a decimal point and two decimals; a rounded zero is `0.00 M€`, never negative zero. A listing is only a potential result, not a completed sale.

Costs come from the current roster's `buyPrice`, through the existing `current_player_acquisition_cost()` mapping. Saved `/roster` responses contain this positive integer field in 118 observed player rows, and the roster parser preserves it separately from market asking prices. The existing `buy_price` and `acquisition_cost` aliases remain supported. No market-value, listing-price or invented-zero fallback is used. Missing costs display `(P/L unavailable)`. A hidden numeric `sale_acquisition_cost` carries the value through display-column filtering, including when **Acquisition Price** itself is hidden; changed costs invalidate the formatted widget payload. Other player tables retain their existing format.

The received-offer panel resolves each offer against the same current roster by player ID and uses the same formatter, so lower competing offers show their own prospective profit or loss. Offers from another context remain excluded.

Performance review: the change adds no API/database reads or writes, persistence layer, timers or dependencies. Configuration and roster observations continue through the existing shared, database-backed resource layer. Added work is bounded scalar cost extraction over squad/offer rows, a single hidden numeric value per squad row, and existing widget schema updates when configuration or cost changes. The existing received-offer regression measured three cold source reads, zero extra panel reads and zero warm reads. No expensive acquisition path changed, so a separate timing benchmark was not warranted. Sale cells put profit/loss on a second line and allow wrapping within the existing table; no fixed widths were added.

Verification (offline): `Rscript test/test_squad_table_prices.R` passed seven focused groups covering known-answer positive/negative/zero amounts, numeric strings, missing costs, listing/offer cells, offer-to-player joins, explicit/unknown/overridden configuration, actual widget schema changes, retained action IDs, hidden purchase-price metadata and reactive cost updates. `Rscript test/test_team_received_offers.R` passed eight existing checks, including shared reads and exact-offer card selection. The repository-required `Rscript test/test_shiny_simulation.R` passed 13 checks plus eight rendered tabs, with no HTTP or live database mutation attempts; it emitted existing empty-trace Plotly warnings. Hosted account testing and a browser/mobile screenshot were not run. The broader unrelated suites were deliberately skipped.

November 2026 mobile layout correction: **Selling by** and **Offer** now render the price and prospective profit/loss as separate block lines, avoiding the table/badge nowrap rule that clipped the combined text. Numeric amounts, sorting, offer titles and the compact received-offer panel stay unchanged. This is a presentation change with no added requests, database work or reactive calculations; each sale cell adds only a small pair of text spans.

Layout verification: all seven focused squad-price checks passed. An offline Playwright check using the real Reactable columns and production CSS confirmed separate price/profit lines fitting all six populated cells at 360, 390 and 1440 px. The table retains horizontal scrolling. Broader suites and hosted testing were deliberately skipped for this display-only change.
