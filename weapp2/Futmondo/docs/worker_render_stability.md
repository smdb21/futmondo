# Stable rendering during background synchronization

The 2026-11-13 blinking-screen report exposed two unnecessary UI publications. Every worker status poll invalidated a process-wide banner dependency, even when the displayed status was unchanged. Separately, a newly received durable snapshot made `shared_resource()` publish stale/loading before replaying that already-decoded local observation. The latter generated two renders for one background update and briefly marked valid displayed data stale.

`fm_worker_notify(account)` now notifies only the affected account. `fm_worker_status_source(session, login)` projects the visible message and oldest source-check timestamp into one session-owned reactive value. Unchanged heartbeat updates produce no output invalidation. Real queue progress, renewal requirements, database-read errors and heartbeat expiry still update the banner. Its observer is destroyed with the session. The existing five-second browser status poll and autonomous worker schedule are unchanged.

`factual_read_adapter()` includes `ready` in its internal replay metadata when the enabled worker already holds that exact scoped snapshot. Expired clause summaries are not ready because their existing fetch contract waits for current verification. `shared_resource()` omits the intermediate loading publication only for a ready replay revision in the same continuously active context and unchanged refresh generation. The final result still passes through the normal cache/state contract. Cold reads, explicit refresh, actual expiry, context changes and failed reads retain their loading/stale behavior. Original source timestamps, validity deadlines and account/league/season/scoring separation are retained. Historical observations never become newly verified because of this display optimization.

These changes add no source acquisition, polling timer, worker service, database table or persistence write. Successful observations continue to be stored by the existing database worker and reused across sessions; the bounded worker memory cache only accelerates reads of those durable records. The new status projection stores one small message/timestamp pair per session. Replay readiness adds one lookup in the existing bounded cache per affected reactive evaluation. Mobile outputs retain their DOM during unchanged polls; actual changed data is rendered once.

Saved-page restoration is a separate path. It now uses the existing foreground-safe read coordinator for at most two attempts with eight-second per-attempt timeouts, while writes remain single attempts. See [page_preferences.md](page_preferences.md) for the response contract and safe failure diagnostics. A production HTTP200 alone could not identify the failure shown in the screenshot; the exact original delivery/parser failure remains unknown.

Verification on synthetic data:

- `test/test_worker_status_redraw.R`: 20 successful polls produce zero repeated renders, source reads or enqueues (0.380 seconds); another account cannot invalidate this banner; real errors/progress and logout/account changes remain visible.
- `test/test_worker_replay_render.R`: five worker updates produce exactly five publications/renders (0.272 seconds), down from ten before the fix; ten unrelated updates produce zero primary renders. Manual Refresh still queues priority10 work and immediately marks old data stale. Expired stored data retains its original source time.
- `test/test_worker_render_browser_app.R` and `test/test_worker_render_browser.cjs`: actual Today cards/shared adapters and synthetic encoded worker snapshots at360/1440px. Two real five-second polls cause zero banner/card redraws; a new balance paints once; heartbeat46/56ms; no horizontal overflow. External requests are blocked. Start the R fixture with its existing test dependencies and run the JS check with `FUTMONDO_TEST_CHROMIUM` if the installed browser is outside Playwright's default location.
- Preference, shared retry/priority, worker live/context, expiry-demand, progressive lineup and clause-scope regressions pass. The required full offline application lifecycle passes13 checks and eight tabs. No real account or transaction is used in tests.

No dependency/environment change or database migration is required. The standing push-triggered Dokploy deployment applies the committed change. Browser tests establish local behavior; the user's authenticated production screen still needs observation after rollout.
